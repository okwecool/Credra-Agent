# Credra Agent 项目展示与面试说明

本文用于准确描述当前 MVP 已经实现并验证的能力，不将规划项表述为已完成功能。

## 简历表述参考

- 构建基于 LangGraph 与 SQLite Checkpoint 的企业授信尽调长任务 Agent，实现任务暂停、人工审核和跨 Python 进程恢复。
- 使用确定性 Python Tool 完成财务指标计算，以状态规则驱动正常与风险 Case 的动态路径，并通过 Pydantic 约束业务数据。
- 将 Research 能力隔离为 stdio MCP Server，支持公司与行业调查工具、来源标识、独立重试及失败信息披露。
- 设计版本化 Artifact Store，使 Graph State 仅保存引用和路由字段；补充调查生成新版本且不覆盖历史证据。
- 实现 JSONL Trace、可控 fail-first 故障注入和固定回归 Case，覆盖 Node、Tool、Retry、Interrupt 与 Resume 关键事件。

建议附上可量化结果时，以仓库当前测试输出为准，不在简历中写死容易过期的测试数量。

## 三分钟项目介绍

Credra Agent 不是自动放贷系统，而是用企业授信尽调验证 Durable Agent Runtime。正常企业直接完成财务分析、风险分析与报告；风险企业先通过 MCP 补充调查，再进入人工审核。任务状态保存在 SQLite Checkpoint 中，因此启动进程退出后，新进程仍可凭同一 `thread_id` 恢复。大块业务结果保存在版本化 Artifact 中，State 只存引用。财务公式、异常检测和路由保持确定性，Retry 耗尽会显式披露调查不完整，避免模型或工具失败被静默掩盖。

## 核心面试问题

### 为什么不用 LLM 决定所有路由？

当前异常规则已知且需要可复现。规则路由便于测试、审计和解释；LLM 更适合处理非结构化表达，而不应替代确定性的财务计算或已知规则。

### 为什么 Checkpoint 不能只放在 UI Session？

长任务生命周期可能长于 UI 和 Python 进程。状态只保存在内存会使刷新页面、进程崩溃或部署重启直接丢失任务，SQLite Checkpoint 提供了最小持久化边界。

### 如何证明 Resume 没有从头重跑？

用相同 `thread_id` 在独立进程执行 `status/resume`，从 Checkpoint 恢复 pending interrupt；测试同时检查已完成节点的执行次数和 Artifact 版本，防止副作用重复。

### 为什么 State 与 Artifact 分离？

Checkpoint 应保存恢复与路由所需的小状态。原始资料和分析结果较大且需要版本化、审计和独立读取，因此写入 Artifact Store，State 只保存 `ArtifactRef`。

### 为什么只把 Research 做成 MCP Tool？

Research 最接近可替换的外部能力，适合验证协议边界。财务计算是本地确定性核心，过早 MCP 化会增加进程和协议成本，却不会改善正确性。

### Retry 耗尽后怎么处理？

不会伪造成功，也不会让整个任务无说明地终止。Research Artifact 标记为 `INCOMPLETE`，Graph State、Risk 和最终报告均披露证据缺口，再交由人工判断。

### 当前 LLM 在主链路中的角色是什么？

模型连接配置已经预留并完成独立连通性验证，但当前 Risk 与 Report 主链路使用确定性基线，以保证离线回归稳定。将 LLM 表达层接入主链路属于后续扩展，不能描述为当前已实现功能。

## 展示顺序

1. 正常 Case：展示无 Research、无人工中断的短路径。
2. 风险 Case：展示 MCP 调研与 `WAITING_APPROVAL`。
3. 新进程 Resume：仅用 `thread_id` 审批并生成报告。
4. Retry：开启 fail-first，展示两个 Tool 各一次重试以及 JSONL Trace。
5. 可选补充调查：展示 v1/v2 Artifact 同时保留。
