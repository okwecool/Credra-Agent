具体适配记录：

1. 依赖保持原版本。确认安装的 SqliteSaver.from_conn_string 使用 cls 构造实例后，通过子类观察 get_tuple/put/put_writes，不修改 Checkpoint 内容。
2. FastMCP StdioTransport 默认 keep_alive=True。日志宿主可能变化，因此有活动服务上下文时为每次会话创建 keep_alive=False 的传输，使用当时的端点；原查询参数/结果语义保留。
3. MCP 工具增加可选诊断上下文；子进程返回 `_service_log_available` 技术字段，客户端消费后移除，再验证原 ResearchQueryResult。子日志失败使父服务暂停后续节点，业务结果继续保存，不作为工具失败重试。
4. TraceEvent 拒绝新增字段，继续采用任务/行号引用桥接；不改旧 Trace JSON Schema。读取行号并追加写入使用进程内锁，跨进程 Trace 写入并发仍沿用旧系统边界。
5. HTTP 响应头的 x-request-id 才用作请求 ID，completion ID 不替代；缺少响应/usage 时保留未知。SDK 日志不格式化原 msg/args/exc_info，异常保留受限位置引用。
6. baseline 的可恢复执行单位是节点，日志故障让当前节点按既有有界逻辑保存结果，在下一节点前暂停。P14 才增加逐 Action/请求账本；没有把中途外调终止冒充安全的日志恢复。

## P12/P13 Coordinator 闭环与执行门禁

| 范围 | 实现 |
|---|---|
| 单步决策 | 新增 `credra_agent.planning.Coordinator`；每轮只向结构化模型提供 TaskSpec、受限假设、Observation 索引、实际可执行工具 Schema、Coverage 和预算快照，只接受一个 ACTION 或 FINISH |
| 公开过程 | Coordinator Prompt 独立版本化；模型只返回简短 `reason_summary`，不持久化或展示思维链；工具完整结果写 Artifact，下一轮只读取摘要和引用索引 |
| 动态重规划 | 每次 Observation 的状态、缺口、增量键和引用进入下一轮输入；同一 TaskSpec 可因首轮缺口选择不同 query/category 的后续 Action |
| 运行授权 | `RunAuthorization` 将授权 ID、提供方、TaskSpec 版本、批准状态、三类预算上限和 Coordinator 限制绑定为单一输入；APPROVED 缺少任一上限时契约拒绝，版本不匹配时不调用模型 |
| 能力边界 | 模型目录取注册表与实际 Handler 的交集；`compare_peers`、`run_scenario` 仍不可用，未注入 Handler 的工具不会展示或派发；`ask_user` 由 Coordinator 内建处理 |
| 执行策略 | Action 在执行前校验工具 Schema、主体、期间、来源 allow/deny/preferred、引用和重复签名；连续无增量达到显式限制后只允许澄清或结束，不静默扩大范围 |
| 预算 | Coordinator 只从 `RunAuthorization` 创建 `BudgetLedger`；模型调用按最大 attempt/总 Token 先预留，并单独限制结构化输出 Token。单阶段首轮成功且 usage 完整时按实际值结算；重试、两阶段或 usage 缺失时按预留值保守结算并标记 uncertain；工具同样先预留再派发 |
| 完成门禁 | 模型 FINISH 只是建议；ANSWERED 必须由 Observation 证明全部必答问题已覆盖，且没有缺口、未解冲突或复核要求。NO_RESULT 不能转为无风险或完成；预算不足、模型不可用、无进展和轮次耗尽统一输出 LIMITED 与 Coverage |
| 兼容降级 | 可选 deterministic/baseline fallback 通过注入适配器返回同一 Decision 契约，随后仍经过相同 ActionPolicy、预算和完成门禁；未配置或输出无效时显式 LIMITED |
| 工件与日志 | 授权原文、每轮模型/工具预算预留与结算、每个获准 Action、工具完整 Payload、Observation 和最终 Coverage 使用 run 内不可覆盖 JSON 工件；Action 通过 `budget_ref` 关联预算记录；记录 PLAN_CHANGED、ACTION_STATE、BUDGET_STATE、STOP，并在每次模型/工具动作前执行日志健康门禁 |

P12/P13 切片采用依赖注入的 StructuredModel 和 Action Handler，验证中只使用固定模型与内存 Provider。当时没有接入自然语言生产入口或旧六节点 Graph，也没有提供可恢复 Action 账本；后续 P14 已增加独立的版本化 Runtime 与账本，但仍不宣称网络调用 exactly-once。

计划中的 12 轮、20 次外部请求、连续 2 次无增量仍是未确认候选值。实现没有把它们写成配置默认值；可信运行入口必须显式构造 `RunAuthorization`，Coordinator 不接受零散上限或外部预建账本。D05 未确认时，生产入口不会创建 APPROVED 授权，也不会触发真实模型或来源调用。当前 `authorized_by` 是审计来源声明，P14 由生产 Runtime 负责生成和持久化，不能接受模型自行填写。

P12/P13 验收覆盖：显式“新增监管消息”问题即使没有 baseline 异常也触发搜索；首轮缺口使第二轮改变 query/category；非法主体、跨期、放宽 allowlist、删除 denylist、丢弃用户来源优先级均在 Handler 前拒绝；重复动作不产生第二次工具调用；NO_RESULT 无法通过 ANSWERED 门禁；模型与工具预算均先预留；预算未确认不调用模型；usage 缺失、重试和两阶段调用按预留量结算；模型失败形成需要复核的 LIMITED，或通过相同门禁执行受限 fallback；APPROVED 缺少上限和 TaskSpec 版本错配均在模型前拒绝；模型/Action 预算工件记录成功、未知用量或拒绝状态。该节点标准脚本曾通过 Ruff lint/format（161 个 Python 文件）、280 项 pytest、`pip check` 和独立 MCP stdio smoke，仅保留第三方 Traceloop 既有 Pydantic 弃用警告。整个验证过程没有真实模型或业务搜索调用。

## P14 版本化 Graph 与恢复

| 范围 | 实现 |
|---|---|
| 图版本 | 新增严格的 `legacy_v1/baseline` 与 `agentic_v2/agentic|shadow` 身份契约；旧 Checkpoint 缺少版本时只读解析为 legacy，未知或混合版本拒绝。旧 `start_task` 仍为默认入口 |
| 节点边界 | `agentic_v2` 将模型决策和工具执行拆为 `decide`、`execute` 两个 LangGraph Node；State 只保存版本、状态及 TaskSpec/授权/假设/Observation 索引/Coverage/预算等 Artifact 引用 |
| Action 账本 | 与 Checkpoint 共用 SQLite 文件、使用独立表；Action 在进入执行 Node 前以 task、plan version、确定性 action ID、规范化参数签名和预算操作 ID 落盘，状态为 `RESERVED/DISPATCHED/RESULT_STORED/UNCERTAIN/FAILED` |
| 请求恢复 | `RESERVED` 可继续派发；`RESULT_STORED` 从不可覆盖 Observation Artifact 重放；`DISPATCHED` 表示请求可能已经发生，恢复时转 `UNCERTAIN`、停止为 LIMITED，不自动重发 |
| 持久预算 | 模型和工具分别以稳定 operation ID 在 SQLite 先预留、派发后结算；外部请求、Token 和累计活动时长跨进程保留。请求窗口不确定时按预留量计费并标记 usage uncertain |
| 状态投影 | Runtime 状态查询先读 Checkpoint 身份再选择旧图或新图；新图输出 `WAITING_CLARIFICATION`、`LIMITED`、`COMPLETED/FAILED`，服务日志状态白名单补充 LIMITED |
| 日志 | 新 Node 包装器统一记录 NODE_START/NODE_END 和前后 TASK_STATE；Action、工具派发/结果、持久预算快照分别记录 ACTION_STATE、TOOL_START/TOOL_END、BUDGET_STATE；生产模型网关继续记录每次 LLM attempt 与返回状态 |
| 显式入口 | 新增 `start_agentic_task` 与 `resume_agentic_task`，调用方必须提供已绑定 TaskSpec、`RunAuthorization`、模型和真实 Handler。P14 不生成隐式批准预算，也不改变 CLI/Chainlit 的 baseline 默认入口 |

故障窗口遵循保守的 at-most-once 恢复策略，而非 exactly-once：决策后的 Action 已入账但图节点未提交时，恢复从账本补回 active action；外部 Handler 已返回但 Observation 未落盘时无法证明请求结果，恢复转为 LIMITED；Observation 和结果指纹已经入账但执行节点未提交时，恢复重放 Observation 并继续下一次决策。结果指纹用于审计与去重判断，不作为能够撤销第三方副作用的承诺。

`shadow` 保留在版本契约中，但 P14 的显式启动入口只接受 `agentic`。架构约定的 shadow 还需要把模型计划旁路到实际 baseline 执行；在这条双运行链路实现前拒绝启动 shadow，避免把“只记录计划”错误实现成真实工具派发。自然语言解析产生的 TaskSpec 已可传给显式 Runtime，但 D05 未确认，产品入口不会自行构造 APPROVED 授权或触发真实模型/来源。

P14 定向验收使用固定模型和本地 Handler：决策后、请求后、结果落盘后三个窗口均通过 `os._exit(91)` 真正终止 Python，再由全新进程读取同一 SQLite/Artifact 恢复；外部调用计数均为一次，请求后窗口投影 LIMITED 且预算 uncertain，结果后窗口最终完成。另覆盖旧版本解析、未知版本拒绝、非法账本状态迁移、持久活动时长上限、模型 fallback、shadow 拒绝、agentic 状态查询和服务日志事件。P14 定向 12 项；最终标准脚本通过 Ruff lint/format（168 个 Python 文件）、292 项 pytest（119.56 秒）、`pip check` 和独立 MCP stdio smoke；仅保留第三方 Traceloop 既有 Pydantic 弃用警告。
