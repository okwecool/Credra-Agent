# Credra Agent MVP 演示指南

本指南用于按固定顺序展示 MVP 的四条关键能力。所有命令均从仓库根目录执行。

## 演示前准备

```powershell
conda activate env_agent
python -m pip check
```

每次演示使用新的 `thread_id`，避免与已有 SQLite Checkpoint 冲突。

## Demo 1：正常Case

```powershell
python -m app.task_cli start `
  --thread-id showcase-normal-001 `
  --case-id case_normal
```

观察点：

- `risk_level=LOW`；

## M2：可插拔互联网搜索与事实核查

M2 保持 MCP Tool 名称 `search_company` 与 `search_industry` 不变，通过 `RESEARCH_PROVIDER` 切换实现：

- `tavily`：实时互联网搜索，当前默认；
- `snapshot`：读取此前实时搜索保存的脱敏 JSON 快照，不访问网络；
- `mock`：固定离线回归数据，只用于开发和测试。

### 1. 配置 Tavily

将 `.env.example` 中以下字段复制到由用户维护的 `.env` 并填写 Key。不要把真实 Key 写入命令历史、日志或提交：

```dotenv
RESEARCH_PROVIDER=tavily
TAVILY_API_KEY=replace-with-your-key
TAVILY_BASE_URL=https://api.tavily.com
SEARCH_DEPTH=basic
SEARCH_MAX_RESULTS=5
SEARCH_TIMEOUT_SECONDS=15
SEARCH_TIME_RANGE=year
SEARCH_SNAPSHOT_DIR=data/search_snapshots
SEARCH_SAVE_SNAPSHOTS=1
CONTENT_FETCH_PROVIDER=auto
SEARCH_CONTENT_SNAPSHOT_DIR=data/content_snapshots
SEARCH_FETCH_TIMEOUT_SECONDS=15
SEARCH_FETCH_MAX_BYTES=5000000
SEARCH_FETCH_MAX_TEXT_CHARS=2000000
SEARCH_FETCH_MAX_REDIRECTS=3
SEARCH_FETCH_MAX_CONCURRENCY=3
SEARCH_FETCH_MAX_CANDIDATES=10
SEARCH_FETCH_MAX_PDF_PAGES=200
FACT_VERIFIER=rules
FACT_VERIFIER_MODEL=
# 可选；不配置时继承 ANALYSIS_LLM_ENABLE_THINKING
# FACT_VERIFIER_ENABLE_THINKING=false
FACT_VERIFIER_MIN_CONFIDENCE=0.75
FACT_VERIFIER_MAX_CANDIDATES=10
FACT_VERIFIER_MAX_INPUT_CHARS=30000
FACT_VERIFIER_TIMEOUT_SECONDS=30
FACT_VERIFIER_MAX_RETRY=1
VERIFICATION_SNAPSHOT_DIR=data/verification_snapshots
```

默认使用 `basic`，且不请求 Tavily Answer 或 Raw Content。成功响应只保存查询、标题、URL、摘要、相关度和检索时间，不保存 API Key。

### 2. 最小真实搜索验证（1 次 API 调用）

这一步会消耗一次真实搜索调用，必须显式授权。建议先确认终端提示符为 `(env_agent)`；若当前为 `(base)`，先执行 `conda activate env_agent`：

```powershell
$env:RUN_LIVE_SEARCH_SMOKE = "1"
python -m tests.live_search_smoke
Remove-Item Env:RUN_LIVE_SEARCH_SMOKE
```

预期输出包含 `provider=tavily`、监管处罚查询、结果数以及一个或多个真实 URL。若没有结果，`results=0` 是有效的空结果；401、429、额度不足、超时和网络错误会显式失败，不会混入 Mock 数据。

### 3. 最小真实正文抓取验证（1 个公开 URL）

M2.1-B 会对通过确定性过滤的候选 URL 做受控 HTML/PDF 抓取。`CONTENT_FETCH_PROVIDER=auto` 时，Tavily 自动使用 HTTP 抓取，Snapshot 自动离线回放，Mock 禁用正文抓取。抓取器只接受公网 HTTP/HTTPS，逐次校验重定向，并限制响应字节、正文字符、PDF 页数、并发数和候选数。

以下 smoke 不调用 Tavily，但会真实访问你指定的 1 个公开 URL。建议选择可直接访问的 HTML 公告页或体积小于 `SEARCH_FETCH_MAX_BYTES` 的文本型 PDF：

```powershell
$env:RUN_LIVE_CONTENT_FETCH_SMOKE = "1"
$env:LIVE_CONTENT_FETCH_URL = "https://example.com/public-report.html"
python -m tests.live_content_fetch_smoke
Remove-Item Env:RUN_LIVE_CONTENT_FETCH_SMOKE
Remove-Item Env:LIVE_CONTENT_FETCH_URL
```

预期 `status=SUCCESS`，并输出 `content_kind`、字节数、字符数、段落或页码数量和 `document_hash`。输出不会打印正文。登录墙、私网地址、HTTPS 降级重定向、超时、超大响应、不支持的类型、加密或无文本 PDF 会以明确 `error_code` 失败，不会被当成已核验事实。

成功正文写入运行时目录 `data/content_snapshots/`，该目录已被 Git 忽略。正文始终标记为不可信输入；M2.1-C 已实现受约束 Claim 核验，只有通过规则或显式启用的 LLM Verifier、并能回查正文位置的事实才可进入 Risk/Report。页面提示注入信号会保留在隔离的正文元数据中，不会被当作系统指令执行。

### 4. 完整场景验证（Intent 驱动，调用数按类别变化）

比亚迪基线首次运行会在 Risk 节点等待人工审核。选择补充调查后，系统会把异常、当前风险项和人工意见归一化为 `InvestigationIntent`，只执行对应类别的查询，不再固定执行全部 7 个企业类别和 1 个行业类别。若人工意见明确包含“监管处罚”“诉讼”“债务”“控制权”或“行业景气”等语义，Query Plan 会记录对应类别及与上一版本的增删差异；Tool Retry 会增加实际调用次数。

新任务的运行 Artifact 与报告按 `case_id + run_id` 隔离，因此可直接复用主 Case，不需要复制源文件：

```powershell
$threadId = "byd-m2-$(Get-Date -Format 'yyyyMMdd-HHmmss')"
python -m app.task_cli start `
  --thread-id $threadId `
  --case-id case_byd_002594
python -m app.task_cli resume `
  --thread-id $threadId `
  --decision research `
  --comment "使用公开互联网来源补充核查监管处罚和债务风险。"
```

任务完成调查后会再次进入 `WAITING_APPROVAL`。检查 Research Artifact：

```powershell
$status = python -m app.task_cli status --thread-id $threadId | ConvertFrom-Json
$runDir = ".\data\case_byd_002594\runs\$($status.state.run_id)"
Get-Content "$runDir\artifacts\investigation_intent_v1.json"
Get-Content "$runDir\artifacts\query_plan_v1.json"
Get-Content "$runDir\artifacts\research_result_v1.json"
```

先观察 Query Plan 的触发来源、类别、查询文本、`added_queries` 和 `removed_queries`；再观察 Research Artifact 的三层产物：`evidence` 保存全部已处理结果，`candidate_evidence` 保存通过确定性过滤的候选证据，`facts` 只保存已核验事实。单条证据的 `subject_match`、`category_match`、`filter_reasons` 和 `evidence_stage` 分别说明主体匹配、类别匹配、拒绝原因和所处阶段。

M2.1-B 还会输出 `content_fetch_status`、`fetched_content_count`、`failed_content_count` 和 `content_fetch_incomplete`。候选项的 `fetched_content` 只保存 URL、类型、标题、日期、正文哈希、段落或页码位置、快照 ID、提示注入信号及错误分类，不把整篇正文复制进 Research Artifact。`COMPLETE` 表示候选正文均抓取成功，`PARTIAL` / `FAILED` / `DISABLED` 会让调查结果保持不完整并显式传递，但不会把已经成功的 Tavily 搜索误记为 MCP Tool 执行失败。

来源等级、主体命中、类别关键词命中和最低相关度只负责筛选候选证据，不会把搜索摘要直接升级为确定事实。公司查询中的 C 级来源还必须在标题命中目标主体或别名；仅正文/摘要偶然提及目标的结果会以 `SUBJECT_TITLE_MISMATCH` 在正文抓取和模型核验前拒绝。A/B 级来源仍允许标题较通用但正文主体明确的公告或权威报道。Web/Tavily 与 Snapshot 结果在完成正文抓取和事实核验前均保持 `UNVERIFIED`；只有显式的离线可信测试夹具，或后续核验阶段确认的证据，才会进入 `facts` 并传递给 Risk 和报告。`execution_status` 表示搜索工具是否执行成功，`verification_status` 表示当前是否已有可作为事实使用的证据，两者不能混用。

### 5. Snapshot 无网络回放

成功的 Tavily 搜索在 `SEARCH_SAVE_SNAPSHOTS=1` 时写入 `data/search_snapshots/`。把用户维护的 `.env` 改为：



### 7. M2.1-C Claim 与正文级事实核验

`FACT_VERIFIER` 支持以下模式：

- `rules`：默认离线模式；只有正文包含与稳定 Claim 完全一致的规范化文本时才接受 `SUPPORTS`，其余语义判断保持 `INSUFFICIENT`；
- `llm`：使用 `MODEL_BASE_URL`、`MODEL_API_KEY`，并优先使用 `FACT_VERIFIER_MODEL`；该字段为空时复用 `MODEL_NAME`。`FACT_VERIFIER_ENABLE_THINKING` 可单独覆盖思考模式，未配置时继承 `ANALYSIS_LLM_ENABLE_THINKING`；
- `disabled`：保留候选和正文记录，但不执行核验，并显式披露 `verification_incomplete`。

每个候选的 `verification_claim` 由主体和调查类别确定性生成；模型只能返回 `SUPPORTS`、`REFUTES`、`IRRELEVANT` 或 `INSUFFICIENT`。`SUPPORTS/REFUTES` 的短证据必须能在指定 HTML 段落或 PDF 页码回查，否则以 `EVIDENCE_MISMATCH` 降级。A/B 级可靠来源才能形成 `SUPPORTED`；两个不同域名且正文哈希不同的来源才能形成 `CORROBORATED`；支持与反驳并存时为 `CONFLICTING`，不进入 `facts`。

核验请求同时携带严格 JSON Schema，固定主体和关系枚举；模型返回布尔主体标记、自造关系值或额外字段时会执行受限应用级重试，耗尽后标记 `INVALID_OUTPUT`。OpenAI SDK 隐式重试已关闭，实际尝试次数只由 `FACT_VERIFIER_MAX_RETRY` 控制。核验缓存写入 `data/verification_snapshots/`，该目录已被 Git 忽略。缓存键包含 URL、正文哈希、Claim、模型、Prompt 版本和置信度门槛。`FACT_VERIFIER_MAX_CANDIDATES` 当前按一次 MCP Tool 调用限制候选数；公司和行业调查分别执行，因此完整调查的理论上限是该值的两倍。超额候选、模型错误、输出不合法、正文缺失和证据无法回查都会显式保留错误分类，不会回退为 Mock。

#### 单文档真实模型 smoke

这一步不调用 Tavily，也不重新抓取网页；它读取 `data/content_snapshots/` 中已经存在的正文快照，并调用一次已配置的模型。将以下环境变量中的 URL 替换为此前成功抓取时使用的原始 URL：

```powershell
$env:LIVE_CONTENT_FETCH_URL = "https://example.com/public-report.html"
$env:LIVE_VERIFICATION_SUBJECT = "比亚迪股份有限公司"
$env:LIVE_VERIFICATION_ALIASES = "比亚迪,002594"
$env:LIVE_VERIFICATION_CATEGORY = "debt"

python -m tests.live_fact_verifier_smoke

Remove-Item Env:LIVE_VERIFICATION_CATEGORY
Remove-Item Env:LIVE_VERIFICATION_ALIASES
Remove-Item Env:LIVE_VERIFICATION_SUBJECT
Remove-Item Env:LIVE_CONTENT_FETCH_URL
```

预期输出包含模型名、执行状态、Relation、主体匹配、置信度、是否接受、证据位置、缓存命中和错误分类，但不会打印正文或真实 API Key。模型结论可以是 `SUPPORTS`、`REFUTES`、`IRRELEVANT` 或 `INSUFFICIENT`；关键门禁是 `execution_status` 不为 `FAILED`，且直接支持或反驳时必须返回可回查的 `evidence_location`。

查看完整场景 Artifact 时，额外观察：

- `verification_execution_status`、`completed_verification_count`、`failed_verification_count` 和 `verification_incomplete`；
- `evidence[*].verification_claim` 与 `evidence[*].verification`；
- `facts[*].claim_id`、`evidence_excerpt`、`evidence_location`、`verifier_model` 和 `verified_at`；
- Risk/Report 中的真实 URL、`evidence_location:*`、`verifier_model:*` 和 `verified_at:*` 引用。

## M3-A：Chainlit 场景化工作台

从仓库根目录启动：

```powershell
chainlit run chainlit_app.py
```

浏览器打开 Chainlit 输出的本地地址，通常为 `http://localhost:8000`。首页会列出 `data/` 下所有具有 `source/` 的合法 Case，并在不修改输入的前提下显示预检状态、警告和人工确认项。

建议按以下顺序验收：

1. 点击“启动 `case_normal`”，确认状态为 `COMPLETED`，Research 和 Approval 显示为本轮跳过，Report Artifact 为 `output/credit_report.md`；
2. 点击“启动 `case_risky`”，确认状态为 `WAITING_APPROVAL`，当前节点为 `risk`、下一节点为 `approval`，并显示风险项与 Evidence；
3. 点击“补充调查”，输入明确意图，确认任务 Resume 后更新 Intent、Query Plan、Research 和 Risk Artifact 版本；
4. 点击“批准并继续”，输入人工审核意见，确认状态进入 `COMPLETED`；
5. 刷新页面后点击“恢复已有任务”，输入刚才的 Thread ID，确认仍可从 SQLite Checkpoint 读取状态。

Chainlit 回调运行在异步事件循环中，工作台通过后台工作线程调用同步 Durable Runtime，避免 MCP 同步客户端与 UI Event Loop 冲突。CLI 与 UI 仍使用完全相同的 Checkpoint 和 Artifact；工作台没有复制任务状态。

M3-A 提供 Case 选择、输入预检、状态总览、节点进度、Artifact 引用、HITL 操作和任务恢复。M3-B 已补充调查计划、Evidence、正文/Verifier 状态、Artifact 版本历史和 Retry/Trace 摘要；M3-C 已提供安全的 Markdown/HTML 报告预览与下载。

## M4-A：主链路受约束 LLM 风险解释

M4-A 将模型调用放在确定性 `Risk` 节点之后。模型只接收已生成的风险等级、风险项、风险描述和每项允许引用的证据 ID，必须输出受 Pydantic 约束的 JSON；系统会逐项校验 `risk_id` 与证据归属。它不能调用 Tool、不能引入 URL、数值或外部事实，不能改变风险等级、Graph Routing 或 HITL 决策。M4-C1 已在最终报告中消费通过二次校验的解释；Risk 节点本身的边界不变。

默认配置为 `ANALYSIS_MODE=deterministic`，不消耗模型额度，但仍在 Risk Artifact 旁写入 `risk_narrative_vN.json`，其执行状态为 `NOT_REQUESTED`。如需进行一次真实主链路验证，请先在用户维护的 `.env` 中配置 `MODEL_BASE_URL`、`MODEL_API_KEY` 和 `MODEL_NAME`（或 `ANALYSIS_MODEL`），然后在当前 PowerShell 会话显式启用：

```powershell
$env:RESEARCH_PROVIDER = "mock"
$env:CONTENT_FETCH_PROVIDER = "disabled"
$env:ANALYSIS_MODE = "llm"
# qwen3.7-plus 默认开启思考；JSON Mode 验收必须显式关闭
$env:ANALYSIS_LLM_ENABLE_THINKING = "false"
$threadId = "m4a-risk-$(Get-Date -Format 'yyyyMMdd-HHmmss')"

python -m app.task_cli start `
  --thread-id $threadId `
  --case-id case_risky

$status = python -m app.task_cli status --thread-id $threadId | ConvertFrom-Json
$runDir = ".\data\case_risky\runs\$($status.state.run_id)"
Get-Content "$runDir\artifacts\risk_narrative_v1.json"
Get-Content ".\traces\$threadId.jsonl" | Select-String '"event_type":"LLM_CALL"'

Remove-Item Env:ANALYSIS_MODE
Remove-Item Env:ANALYSIS_LLM_ENABLE_THINKING
Remove-Item Env:CONTENT_FETCH_PROVIDER
Remove-Item Env:RESEARCH_PROVIDER
```

预期：`case_risky` 仍进入 `WAITING_APPROVAL`；`risk_narrative_v1.json` 的 `execution_status` 为 `COMPLETE`，每个 `explanations[*].evidence_ids` 只来自同一 `risk_id` 的确定性风险证据；Trace 至少包含 `purpose=risk_narrative` 的一条 `LLM_CALL/SUCCESS`。若本轮进入 Research，还会包含 M4-B 的 `purpose=evidence_summary_query_proposal` 调用。Trace 仅记录模型名、Prompt 版本、次数和 Token 统计，不记录 Prompt、模型原文、正文或 API Key。

如果模型 Key 缺失、Provider 不可达、响应不是合法 JSON，或引用了不允许的证据，预期 Artifact 为 `DEGRADED` 且 Trace 为 `LLM_CALL/FAILED`；任务仍应保持原有的 `WAITING_APPROVAL` 或 `COMPLETED` 状态。这个降级结果是安全预期，不应通过重试后把未经校验的文本写入 Risk 或报告。

## M4-B：Evidence Summary 与受约束 Query Proposal

M4-B 在 Research 节点完成确定性 Investigation Intent、Query Plan、Candidate/Verified Evidence 后运行。模型只收到紧凑的 Evidence 索引、已核验 Fact（若有）、证据缺口和规则 Query Plan 约束；它不会读取被拒绝 Evidence、正文快照或执行搜索。

沿用上节的 `ANALYSIS_MODE=llm` 演示命令，在 `$runDir` 下额外检查：

```powershell
Get-Content "$runDir\artifacts\evidence_summary_v1.json"
Get-Content "$runDir\artifacts\query_proposal_v1.json"
Get-Content ".\traces\$threadId.jsonl" |
  Select-String 'purpose=evidence_summary_query_proposal'
```

验收点：

1. `evidence_summary_v1.json` 的每个条目保留确定性的 `SUPPORTED`、`CORROBORATED`、`CONFLICTING` 或 `UNVERIFIED` 状态；候选或冲突证据不会被模型提升为事实；
2. 每个条目同时绑定 `evidence_id`、`source_id`，以及可用时的 `claim_id`、`fact_id`；`summary_evidence_ids` 仅列出已核验的 Evidence；
3. `query_proposal_v1.json` 的 `allowed_categories` 与 Intent 一致。每条 Proposal 都标为 `ACCEPTED_FOR_REVIEW` 或 `REJECTED` 并保留拒绝原因；即使被接受也不会执行，`query_plan_v1.json` 不会被改写；
4. `LLM_CALL` Trace 的输入摘要为 `purpose=evidence_summary_query_proposal`，不含模型文本、正文、URL 或 API Key；
5. 模型输出越界、非法或不可用时，上述两个 Artifact 都是 `DEGRADED`，而确定性 `research_result_v1.json` 与 `query_plan_v1.json` 仍可继续进入 Risk/HITL。

## M4-C：Report Draft 与最终报告二次校验

沿用 M4-A/B 已停在 `WAITING_APPROVAL` 的 `$threadId`。批准后，Report 节点会新增一次 `purpose=report_draft` 的结构化模型调用：输入仅为确定性的 Company/Financial/Risk/Verified Fact 来源索引，不包含人工意见、正文或 URL。输出写入 `report_draft_v1.json`，随后 M4-C1 重建来源索引并完成第二次校验，再生成最终报告：

```powershell
python -m app.task_cli resume `
  --thread-id $threadId `
  --decision approve `
  --comment "已核对模型引用与确定性结论，继续生成报告。"

$status = python -m app.task_cli status --thread-id $threadId | ConvertFrom-Json
$runDir = ".\data\case_risky\runs\$($status.state.run_id)"
Get-Content "$runDir\artifacts\report_draft_v1.json"
Get-Content "$runDir\artifacts\report_expression_v1.json"
Get-Content "$runDir\output\credit_report.md"
Get-Content ".\traces\$threadId.jsonl" | Select-String '"event_type":"LLM_CALL"'
```

验收点：

1. 状态为 `COMPLETED`，State 同时包含 `report_draft_artifact=artifacts/report_draft_v1.json` 和 `report_expression_artifact=artifacts/report_expression_v1.json`；
2. `report_draft_v1.json` 的 `execution_status=COMPLETE`，Executive Summary 和每个固定类别段落均携带 `reference_ids`，Trace 新增且只新增一条 `purpose=report_draft` 调用；
3. `report_expression_v1.json` 记录 `COMPLETE`、`PARTIAL` 或 `FALLBACK`，并列出来源指纹复核后的接受表达与 `unsupported_claims`；
4. 报告显示“执行摘要（受约束模型表达）”“受约束 Evidence Summary”“受约束 LLM 风险解释”和“模型表达审计”，但财务数字、风险等级及人工意见仍来自确定性 Artifact；
5. 新增调查建议均显示 `NOT_EXECUTED`，不会修改 Query Plan 或自动访问互联网；
6. 若模型配置缺失、调用失败、来源指纹变化，或输出包含未知 URL、数字、Evidence/Fact/Metric/Risk 引用，报告仍成功生成，并把对应表达排除或回退为确定性内容。

`ANALYSIS_MODE=deterministic` 时不执行上述第三次调用，但仍生成 `report_draft_v1.json`，其状态为 `NOT_REQUESTED`，最终确定性报告正常完成。真实 Qwen 验收会消耗一次额外调用；执行前应确认额度并使用新的 Thread，普通 `pytest` 和 `scripts/verify.ps1` 始终强制离线。

## M5-B：导出单次任务审计包

先完成一次新式 Durable Task；可以沿用本指南前面已经 `COMPLETED` 的 `$threadId`。从仓库根目录执行：

```powershell
$audit = python -m app.audit_cli export `
  --thread-id $threadId | ConvertFrom-Json

$audit
Get-FileHash -Algorithm SHA256 $audit.archive_path
```

预期 CLI 返回 `case_id`、`thread_id`、`run_id`、相对 `archive_path`、`archive_sha256`、文件数和 Artifact 数；`Get-FileHash` 的值应与 `archive_sha256` 一致。导出只读取现有 Checkpoint、Run Artifact、报告、来源清单和受限 Trace 元数据，不会调用 Tavily/Qwen。

可将 ZIP 解压到一个新的检查目录：

```powershell
$inspectDir = "audit-exports/inspect-$(Get-Date -Format 'yyyyMMdd-HHmmss')"
Expand-Archive -LiteralPath $audit.archive_path -DestinationPath $inspectDir

Get-ChildItem $inspectDir -Recurse
Get-Content "$inspectDir/manifest.json"
Get-Content "$inspectDir/artifact_manifest.json"
Get-Content "$inspectDir/runtime_metrics.json"
```

重点核对：

1. 包中有 `report.md`、`report.html`、`source_manifest.json`、`evidence.json`、`artifact_manifest.json`、`trace_summary.json`、`runtime_metrics.json`、`manifest.json` 和 `artifacts/`；
2. `manifest.json` 中每个成员的大小和 SHA-256 与解压文件一致，`artifact_manifest.json` 同样覆盖全部版本化 Artifact；
3. `trace_summary.json` 只有聚合计数和时间范围，不含原始 `input_summary`、`output_summary` 或 Trace 行；
4. `runtime_metrics.json` 显示 Search/LLM/Retry/Interrupt/Resume、Token、人工等待、Artifact 数和从历史 Artifact 推导的可观测执行模式；当前 Trace 无法提供 Provider API credits，现有 Artifact 也没有持久化正文抓取 Provider，因此分别明确为 `null` 和 `NOT_RECORDED`，不会使用导出时的当前配置冒充历史配置；
5. 包内没有 `.env`、SQLite Checkpoint、JSONL Trace、搜索/正文/核验 Snapshot、API Key 或本机绝对路径。

若任务使用了自定义运行目录，三个全局参数必须放在 `export` 之前：

```powershell
python -m app.audit_cli `
  --db ".test-tmp/demo/checkpoints/credra.db" `
  --data-dir ".test-tmp/demo/data" `
  --trace-dir ".test-tmp/demo/traces" `
```

第一版只接受状态为 `COMPLETED` 且包含 M2.2 Run ID 的任务。同一输出目录不会覆盖已有同名 ZIP；这是审计包的不可变保护，不是异常恢复逻辑。
