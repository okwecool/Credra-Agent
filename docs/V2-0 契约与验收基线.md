## 2. P01：输入、行动与恢复契约

可执行定义见 [contracts.py](../spikes/v2_readiness/contracts.py)，各模型最小实例见 [contract_examples.json](../tests/fixtures/v2_readiness/contract_examples.json)。未知字段默认拒绝，JSON 数值禁止 NaN/Infinity，Decimal 序列化为字符串。

| 契约 | 必需语义与关联 |
|---|---|
| TaskSpec | `schema_version=task_spec_v2`、单调 version、source_message_id、operation、主体、as_of、期间、问题及完成标准、来源策略、条件与未决字段 |
| Plan | plan_id/version、task_spec_version、previous_plan_id、问题/假设/待执行动作引用、公开变更理由 |
| Hypothesis | 问题引用、可证伪陈述、替代解释、支持/反证引用及 OPEN/SUPPORTED/REFUTED/CONFLICTING/UNRESOLVED 状态 |
| Action | action_id、TaskSpec/Plan 版本、工具及对应参数、hypothesis/evidence 引用、预期观察、公开理由 |
| ExecutionRecord | 以 action_id 关联版本、预算预留 ID、attempt、执行状态和 Observation 引用；结果不确定必须保守计账 |
| Observation | observation_id、action_id、attempt、状态、结果 Artifact 引用、受控错误码 |
| Coverage | 必答问题逐项分为已回答或显式缺口；冲突未解必须复核；不能用“无搜索结果”代替回答 |
| BudgetLedger | 人工授权状态、请求/Token 上限、已用与预留、活跃时间上限及未知用量标记；已用超额可以如实入账，但不得再预留 |
| GraphVersion | legacy_v1 仅 baseline；agentic_v2 为 shadow/agentic。表达模式 deterministic/LLM 与执行模式分离 |

TaskSpec 是任务快照；status/pause/resume/amend/approve_report 的解析结果必须绑定持久化任务，再形成新快照或控制命令，不能让每条短指令凭空重建全部字段。此原型没有实现命令解析或应用指令补丁。

### 2.1 自然语言约束

- `preferred` 表示优先顺序，不等于 `allowed`；`allowed=null` 表示没有额外白名单，空白名单、允许/禁止重叠、优先来源在禁止范围均拒绝。
- 缺失主体、相对期间不可比、子公司范围不清或条件相互矛盾时，标记 NEEDS_CLARIFICATION 并列明字段；不能猜测后进入 READY。
- as_of 是知识截止日，期间结束不能越界。证据发布日在 as_of 之后也不得使用；后者由 Evidence/Policy 跨对象校验执行，并非本阶段 TaskSpec 单对象验证已实现。
- 条件指令保留条件、待执行动作和 PENDING/MET/NOT_MET/UNKNOWN；只有条件被证据或计算证实才执行。UNKNOWN 触发补资料或缺口披露。
- 用户文本是业务输入，不提供工具白名单之外的能力，也不能绕过审核、预算或事实核验。

### 2.2 工具参数与业务边界

| 工具 | 参数契约 | 实施阶段 |
|---|---|---|
| read_document / fetch_content | reference_id，必须在当前任务可读索引中解析 | V2-1 |
| search_evidence | 完整 query、subject_id、period、SourcePolicy；Provider 不得重建为固定类别模板 | V2-1 |
| verify_claim | claim_id、非空 source_refs | V2-1 基础能力，V2-2 深化 |
| compute_metrics | metric_ids、非空 input_refs、accounting_basis | V2-1 既有指标，P24 增量 |
| compare_peers | 至少两个 subject_ids、input_refs、metric_ids | V2-3 |
| run_scenario | input_refs、assumption_ref、formula_version | V2-3 |
| ask_user | 问题和非空 unresolved_fields | V2-1 |
| finish | coverage_ref 与业务停止原因 | V2-1 |

模型选到未注册能力时返回 UNAVAILABLE；契约可以提前描述能力，不代表已授权执行。Action 参数由工具专属模型检查，JSON 中 arguments 仍是对象；后续注册表须直接使用这些参数模型，不能只依赖通用 Action 的 JSON Schema。执行前另行检查版本一致、引用存在、主体/日期/来源范围、工具可用和预算授权；单对象 Pydantic 通过不代表 Policy 通过。

### 2.3 状态、停止与计账

Observation 的 SUCCESS 表示调用返回有效结果；NO_RESULT 表示成功查询为空；UNAVAILABLE 表示能力/来源不可用；MISSING_DATA 表示分析缺字段；FAILED 表示技术失败。后面三者有明确 error_code，失败不能回写成零值。

finish 原因为 ANSWERED/BUDGET_EXHAUSTED/NO_PROGRESS/NEEDS_REVIEW。V2-1 Runtime、报告、UI 和导出共享同一持久化字段：`stop_reason`、`coverage_ref`、`limitations`、`review_required`。ANSWERED 必须通过覆盖门禁；预算耗尽或无增量只能形成带缺口的受限结果；技术 FAILED 单独投影，不能伪装业务完成。澄清/审核等待暂停活跃时间计量；等待时长另记。

预算没有确认时保留 UNCONFIRMED，不隐含无限配额；禁止真实调用。Policy 先校验并持久化预留，再派发请求；模型、搜索、抓取、核验、重试和 fallback 都计账。未知 Token 不填零，实际超额如实记录。候选轮次/请求数不在本阶段升级为默认值。

### 2.4 旧任务与不确定请求窗口

| 恢复时观察 | 后续行为 |
|---|---|
| 旧状态没有 graph_version | 只读解析为 legacy_v1/baseline，走旧 Graph；不原地写新字段 |
| 已知显式版本 | 按创建版本恢复；版本与模式不匹配则拒绝 |
| 未知版本 | 明确报错，不尝试以最新 Graph 猜测恢复 |
| RESERVED，尚未派发 | 校验预留和版本后继续；不能额外重复扣同一预留 |
| DISPATCHED，没有已落盘 Observation | 标 UNCERTAIN，保留预算占用；优先查询 Provider 请求状态，无法判定则披露并等待受控决策，不盲目重发 |
| RESULT_STORED 且 Artifact 完整 | 重放已存 Observation，不再外调 |
| Artifact 缺失/损坏或审核版本不符 | 停止恢复并披露；不能沿用旧批准或伪造结果 |

ExecutionRecord 只是状态契约；事务边界、幂等键及上述故障窗口的真实中止验证属于 P14。本阶段实际跨进程验证的是冻结的 legacy Checkpoint，不宣称新 Agent 已可恢复或网络调用 exactly-once。

## 3. P02：证据、结论与财务

### 3.1 v1 映射

| 现有数据 | V2 表达 | 兼容约束 |
|---|---|---|
| source_manifest 来源 ID/链接/说明 | Evidence 的 original_source_id、publisher、定位、内容哈希、发布/事件/获取日期 | 旧缺失字段标未知，不能把清单中存在链接等同于已抓取或已核验 |
| Research Fact / verified fact | Claim + Evidence + 核验状态和 verifier_version | 仅有旧 verified 标记不足以凭空补出原文/哈希；需保留原始记录与映射限制 |
| evidence summary / query proposal | 假设、线索和公开摘要引用 | 待查 Query Proposal 不是已执行 Action，也不是事实证据 |
| risk flags / rule risk level | Assessment.rule_risk_level 及原 rule Artifact 引用 | 规则结果保留，模型分析单独记录，MEDIUM/HIGH 不绕过必审 |
| FinancialYear / 既有 metric | 版本化 FinancialDatum / MetricResult，带原 Artifact 引用 | 不覆盖旧 JSON，不改变旧数值和期望答案 |

Evidence 表达主体、原始来源、发布者、三类日期、原文片段和位置、文档哈希、REAL/SYNTHETIC、可信度、支持关系及核验版本。ACCEPTED 必须带 verifier_version；哈希示例中的全零仅为显式合成占位，不是已核对真实文件。

Claim 将原文主张与系统判断分开。CONFLICTING 必须有支持与反证引用；跨对象检查还要核对引用对象、主体、日期和原文确实支持该关系。转载按 original_source_id 聚合，不按网址数量累计独立印证。声明是当事方证据，不自动升级为独立事实。Assessment 区分规则风险、证据判断、计算与限制，不做贷款决策。

### 3.2 Financial v2 最小约定

用户于 2026-09-08 确认：**新增合并净利润作经营现金流/净利润分母；现有归母净利润保留。新字段缺失时不可计算，不自动替代。**

每个输入独立携带期间、合并/母公司口径、利润归属、原币种/单位、归一单位、修订版本、Decimal 值/缺失原因和来源定位。`metric=net_profit` 时必须区分 GROUP_TOTAL 与 OWNERS_OF_PARENT；现有制造业两例旧字段映射到后者。其他旧案例需逐源确认，不能一概假定归母。

原型只接受 CNY，归一单位 CNY_1000；不把外币值贴上人民币标签。人民币元除以 1000、万元乘以 10、千元不变。多币种需另外定义汇率、日期和来源，未包含在当前最小实现中。

缺失值是 null 加 missing_reason，不补零；负利润/净资产允许如实表达，不复用旧模型中会排除资不抵债状态的约束。P24 负责字段间勾稽、单位换算和口径匹配；本阶段只验证表达。原值、修订前值和重述值分别保留，不自动混接两套期间。

| P24 首例字段/公式 | 计算前提 | 人工算例（合成，千元） |
|---|---|---|
| 应收账款增长 `(AR_t / AR_prev) - 1` | 同主体/期间长度/合并口径；上期值 > 0 | 100 → 140，40% |
| 营业收入增长 `(Rev_t / Rev_prev) - 1` | 同口径，上期值 > 0；营业收入与含利息的营业总收入不混用 | 1000 → 1100，10% |
| 增速差 `AR_growth - revenue_growth` | 两个增速均可计算；结果是百分点 | 40% − 10% = 30 个百分点 |
| 现金利润比 `CFO / consolidated_net_profit` | 同期合并 CFO 和 GROUP_TOTAL 净利润；分母 > 0 | 80 / 100 = 0.8；归母 90 不参与 |

零/负分母、缺失字段、期间或口径不匹配返回 NOT_COMPUTABLE 并说明原因；单项字段可用不代表组合可用。精确 Decimal 人工输入比较不设金额容差；比率验收比较未展示前数值，绝对误差 ≤ 0.000001。展示百分数四舍五入至两位，增长差明确标百分点。真实资料提取如有披露舍入，需要 P20/D04 在逐字段材料表中确认，不能用宽容差掩盖单位错误。

首例最小输入为两期应收/营业收入、当前期合并 CFO/合并净利润及保留归母利润。账龄、票据/合同资产、坏账、受限资金、短债、季度/同业/情景留在后续；若首例必答问题需要这些字段，先确认范围。现阶段不生成真实财务结论。

### 4.3 自然语言基线与人工评分

[natural_language_goldens.json](../tests/fixtures/v2_readiness/natural_language_goldens.json) 有 **32 条**指令，固定参考日、任务上下文、预期操作/语义和禁止行为，覆盖主体歧义、期间、来源优先/仅限、否定、条件、缺失数据、暂停/继续、状态查询、修订、审核版本、转载/异主体、情景和重复指令。它是后续解析器的人工预期，当前没有解析准确率结果。

用户于 2026-09-08 确认五项等权、每项 0–5 分、均分至少 4 分；以下任何硬失败直接不通过：虚构关键事实、数字错误、越权、漏必审、恢复破坏。真实试跑次数/预算仍须 D05/D07 后续确认，本次只冻结评分口径。

| 维度 | Q1 的核对项 | Q2 的核对项 |
|---|---|---|
| 指令遵循 | 期间、主体、合并口径正确，缺失不替代 | 遵守来源限制，覆盖用户要求的反证 |
| 调查决策 | 先取得输入，遇缺失查补或受限停止 | 冲突导致核原文/补证据，不机械重复查询 |
| 证据支持 | 每个输入/公式能追溯 | 不将转载、同名异主体、公司声明当独立事实 |
| 财务正确性 | 四项结果及单位准确 | 不把应收余额等同逾期，不杜撰账龄 |
| 完成与缺口披露 | 回答计算问题，注明不可计算项 | 说明未决冲突、证据限制与必审需求 |

通用评分锚点：5=完整且可复核；4=核心正确、仅次要遗漏且不影响结论；3=部分完成但关键解释/调查不足；2=主要要求未完成；1=只有零散相关输出；0=未完成或与要求相悖。硬失败独立登记，不被分数抵消。每个问题都填五项并附轨迹/Artifact 引用，均分 ≥4 且无硬失败才通过；案例中每个必答问题均须通过，不用总平均掩盖失败问题。

[evaluation.py](../spikes/v2_readiness/evaluation.py) 只聚合人工评分并执行门槛，不自动生成分数，不用模型自评替代审核。

## 5. P04：全服务日志契约

### 5.1 归档与字段

根服务每次启动创建 UTC 时间加随机后缀的 startup_id；MCP 子进程继承端点/批次和临时认证参数。集中写入 `logs/<startup_id>/service.0001.jsonl` 等分卷；下一完整 UTF-8 记录使文件超过 **10,000,000 字节**时先开新卷。精确等于阈值允许写入。超长摘要受限截断并标记，事件元数据不得无界；不拆分 JSON 行，不覆盖历史分卷，不自动删除历史日志。

生产公共字段按开发计划第 10.4 节：原发生时间 timestamp_utc、接收时间、level、event_type/event_id、startup_id/sequence、service/logger、process_instance_id/pid/os_thread_id、业务 thread_id/run_id/case_id、action_id/call_id/attempt、node、from_state/to_state、status/duration_ms/error_code、受限 message。无任务上下文时业务字段为空。接收 sequence 不是严格业务因果时钟；业务关联以 ID 和持久化版本为准。

### 5.2 事件覆盖与结果分层

| 生产事件族 | 必记内容 | 本阶段验证 |
|---|---|---|
| SERVICE / PROCESS | start、config_validated、ready、stop、uncaught_error、子进程连接/退出 | 独立根/子进程与启动清单 |
| TASK / NODE / PLAN | 创建/拒绝、节点开始/完成/失败/跳过、路由、前后状态、计划版本、interrupt/resume/stop_reason | 节点、任务状态与旧 Trace 引用样本 |
| LLM_ATTEMPT | start/first_token/end、调用用途/阶段、provider/model、请求 ID/HTTP 状态、finish_reason、usage、重试/降级 | 合成 attempt 与 INVALID_SCHEMA 汇聚；未模拟真实 Provider |
| LLM_VALIDATION | transport、JSON、schema、citation、business 的独立状态 | 用例证明 schema 拒绝不写成业务成功；完整矩阵在 P15 |
| MCP / TOOL / SOURCE | 会话、调用 ID、工具、query plan、成功/空/超时/限流/失败、耗时 | 两个实际 stdio MCP 子进程 |
| CHECKPOINT / ARTIFACT | 保存/读取/恢复/生成结果、版本、引用、异常 | 契约明确，生产挂点 P15 |
| LOG_PIPELINE | 初始化/轮转/汇聚失败、恢复、完整性缺口 | 轮转、异常帧、认证失败、磁盘失败、收集器退出 |

LLM 传输成功与 JSON/Schema/引用校验分开；未知 usage/HTTP 状态用 null/UNKNOWN，不猜测。原始请求/响应/思维链、完整正文、Key、请求头/Cookie 不入日志；保留受控错误码与安全堆栈位置，禁止局部变量。生产 SDK/URL/异常堆栈脱敏和所有失败矩阵在 P15 验收，不能仅凭原型的字段丢弃宣称全应用已去敏。

### 5.3 IPC、Trace 桥接与持久化保证

Spike 使用认证的 localhost TCP JSON 通道，和 MCP stdio 分离；单写入者在锁内追加、flush/fsync 后 ACK。单帧上限 262,144 字节，socket 等待上限 2 秒是 **Spike 测试参数**，不是已批准生产默认值。ACK 丢失可能仍已落盘；event_id 的去重只在收集器内存存活期间有效，不宣称跨重启 exactly-once。

现有 TraceEvent 禁止额外字段，不能直接塞入 event_id。本阶段不修改旧 Trace；通过 `trace_event_ref=<thread_id>.<line_number>` 关联服务日志，并验证旧 Trace 字节不变。P15 使用桥接层生成一次业务事件、保留稳定引用及防重复处理，不维护第二份业务状态。

写入异常会将 Spike 写入者标为不可继续，并返回受限 stderr/失败 ACK，避免不确定落盘后继续使用相同序号。正常退出等待已接收处理线程并刷新；异常清单不宣称正常完成。强杀前尚未送达的事件、OS 崩溃/硬件缓存、ACK 丢失均可能形成缺口；服务日志不能代替 Checkpoint 恢复。

**用户于 2026-09-08 已确认生产故障策略：** 收集器不可达、队列持续满或磁盘写入失败时暂停派发新 Agent 动作，保留已发生请求的结果，明确提示恢复日志后继续；不自动重跑结果不确定的请求。当前 Spike 使用同步 ACK、没有生产缓冲队列；P15 接入前再提交有界队列容量、持续满判定时长和刷新参数，不能由测试超时值推定生产默认值。关键事件达到持久化条件后再派发动作。
