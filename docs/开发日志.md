## 2026-08-12 — Day 0 Durable Execution Technical Spike

- **对应阶段：** Day 0 — Checkpoint / Interrupt / Kill Process / Resume。
- **文档原约定：** 使用 `node_a → interrupt() → 退出进程 → Command(resume) → node_b` 的最小流程，验证 SQLite Checkpoint、相同 `thread_id` 跨进程恢复，以及恢复后不重新执行已完成节点。
- **实际情况：** LangGraph 在 Resume 时会从包含 `interrupt()` 的节点开头重新执行。若 `node_a` 自身包含 interrupt，无法清晰区分“中断节点按框架语义重新进入”与“中断前已完成节点被错误重复执行”。
- **修改内容：** Spike 调整为 `prepare → approval(interrupt) → complete` 三节点流程；由 `prepare_runs` 记录 interrupt 前已完成节点的执行次数，并通过独立 Python 子进程分别执行 start、status 和 resume。
- **修改原因：** 在遵守 interrupt 节点无副作用约束的同时，准确验证已完成节点不会在跨进程 Resume 后重新执行。
- **影响范围：** 仅影响 Day 0 Spike 的验证结构，不改变后续业务 Graph、MVP 范围或验收目标。
- **验证结果：** SQLite 成功保存线程 Checkpoint；新进程使用相同 `thread_id` 恢复后任务进入 `COMPLETED`，且 `prepare_runs` 保持为 `1`；跨进程自动化测试共 2 项通过。

## 2026-08-12 — Day 1 Core Business Flow

- **对应阶段：** Day 1 — Financial → Risk → Report 最小业务纵向链路。
- **文档原约定：** Risk Agent 和固定模板报告由 LLM 生成表达，并通过 Pydantic Schema 约束结果。
- **实际情况：** 当前尚未配置可供自动化测试使用的模型凭证；若把外部模型调用作为 Day 1 门禁，核心财务公式、Schema 和纵向流程将无法离线稳定回归。
- **修改内容：** 保留外置 Risk/Report Prompt，并先实现确定性的结构化 Risk 基线与固定 Markdown 报告渲染器；财务计算仍全部由 Python Tool 执行。Risk 与 Report 通过独立函数边界提供，后续接入模型适配器时不改变 Financial Tool 和 Pydantic 数据契约。
- **修改原因：** 使 Day 1 纵向链路在无模型凭证情况下可重复测试，同时避免 LLM 参与确定性计算。
- **影响范围：** Day 1 的风险解释和报告文本暂为确定性基线；不影响后续动态路由、Artifact、HITL 或模型接入设计。
- **验证结果：** 两个固定 Case 均完成 Financial → Risk → Report；财务公式、缺失字段、年份顺序和零分母边界测试通过；Risk Pydantic 约束和固定报告章节测试通过；包含 Day 0 回归在内共 14 项测试通过。

## 2026-08-12 — 基础模型连接配置

- **对应阶段：** Day 1 — 配置与 Schema。
- **文档原约定：** 模型配置包含 `MODEL_NAME` 和 `MODEL_API_KEY`。
- **实际情况：** 用户需要自行配置兼容 OpenAI 调用方式的 API Base URL、模型名称和 API Key，以支持非默认模型服务端点。
- **修改内容：** 新增 `MODEL_BASE_URL`，与既有 `MODEL_NAME`、`MODEL_API_KEY` 组成模型连接配置；配置 Schema 提供 OpenAI 默认 Base URL，并将 API Key 读取为自动脱敏的 `SecretStr`，同时增加环境变量加载测试。
- **修改原因：** 允许在不修改应用代码的情况下切换兼容 OpenAI API 的基础模型服务。
- **影响范围：** 仅扩展模型连接配置，不改变当前财务计算、风险 Schema 或报告契约。
- **验证结果：** 环境变量中的 Base URL、模型名称和 API Key 均可正确加载，API Key 在配置对象中以 `SecretStr` 脱敏；包含既有回归在内共 15 项测试通过。

## 2026-08-12 — Day 2 Artifact 与 Dynamic Routing

- **对应阶段：** Day 2 — Document、Artifact、异常检测与动态路由。
- **文档原约定：** Case B 在 Financial 后进入 Research，再进入 Risk；Day 3 才实现 Research Agent 和 MCP Server。
- **实际情况：** Day 2 必须验收 `Document → Financial → Research → Risk` 路径，但本阶段尚无真实 Research Tool，也不应伪造外部调查事实或 Research Artifact。
- **修改内容：** Day 2 的 `research` 节点仅作为无副作用路径标记，证明条件路由选择成功；节点不生成调查事实，`research_artifact` 保持为空。执行路径从 LangGraph 更新流收集，不写入最小 Graph State。Day 3 将用 MCP-backed Research 实现替换该节点。
- **修改原因：** 保持开发阶段边界清晰，在验证动态执行的同时避免提前实现或伪造 Day 3 能力。
- **影响范围：** Case B 的 Day 2 风险分析仍只使用财务 Artifact；Research 数据及其风险证据将在 Day 3 接入。
- **验证结果：** Case A 路径为 `document → financial → risk` 且无异常标记；Case B 路径为 `document → financial → research → risk`，稳定生成 `REVENUE_CASHFLOW_DIVERGENCE` 与 `DEBT_RATIO_RISING`。两组 Case 均生成 Company、Financial、Risk 三类 v1 Artifact，Graph State 保持 13 个最小字段且不包含大块对象；包含既有回归在内共 25 项测试通过。

## 2026-08-12 — Day 3 Research Agent 与 MCP

- **对应阶段：** Day 3 — Research Agent、Research MCP Server、`search_company` 与 `search_industry`。
- **文档原约定：** Research Agent 通过 MCP Client 调用本地 Mock Dataset/Search Adapter，将事实、来源和查询状态写入 Research Artifact。
- **实际情况：** Windows 下若通过文件路径直接执行 `app/mcp/research_server.py`，子进程模块搜索路径只包含脚本目录，无法解析顶层 `app` 包；此外同步 LangGraph 节点需要适配 FastMCP 的异步 Client。
- **修改内容：** 默认 stdio Transport 使用当前解释器执行 `python -m app.mcp.research_server`；同步 Graph 节点通过明确的 `asyncio.run` 边界调用异步 MCP Client，并在检测到已有事件循环时抛出可识别错误。公司与行业两个 Tool 在同一 MCP Session 中顺序调用。测试使用 FastMCP 内存 Transport验证相同协议契约，另提供独立 stdio 子进程验收脚本。
- **修改原因：** 保证项目包导入稳定、Windows 子进程行为可复现，并避免一次调查任务重复建立 MCP Session。
- **影响范围：** Research Agent 的运行边界和测试方式；不改变 Graph State、路由规则或 Artifact 引用结构。异步 Graph 运行方式属于后续扩展项。
- **验证结果：** `search_company` 与 `search_industry` 均通过 MCP 返回带来源标识的结构化事实，未知查询显式返回 `found=false` 和空事实；不可用 Server 被转换为 `ResearchServiceError`。Case A 保持 `document → financial → risk`，Case B 通过独立 stdio MCP Server 完成 `document → financial → research → risk`，生成 `research_result_v1.json`，Risk Artifact 的 evidence 包含 MCP `source_id`；全量 28 项测试及 stdio 子进程验收通过。

## 2026-08-13 — Day 4 HITL 与完整跨进程 Resume

- **对应阶段：** Day 4 — Risk 审核、interrupt、HumanDecision、SQLite Checkpoint、跨进程 Resume 与最小 Chainlit UI。
- **文档原约定：** `MEDIUM/HIGH` 风险进入 `WAITING_APPROVAL`；`APPROVE` 继续报告，`RESEARCH` 补充调查；新进程凭相同 `thread_id` 恢复，Research 重新执行时不得覆盖历史 Artifact。
- **实际情况：** Day 2 的无 Checkpoint Runner 在 Graph 增加 Report/Interrupt 后不再适合完整生命周期；同时 `status/resume` 若要求用户重复提供 `case_id`，会增加恢复错误风险。Chainlit CLI 直接加载 `app/chainlit_app.py` 时只使用该脚本目录解析模块，无法导入顶层 `app` 包。
- **修改内容：** 新增 SQLite-backed Task Runtime，由 Checkpoint 的 `channel_values.case_id` 自动重建 Case Graph；提供 `start/status/resume` CLI。Risk 后按风险等级进入动态 interrupt；Research 决策生成 `research_result_vN` 和 `risk_analysis_vN` 后再次审核。低风险路径扩展为 `document → financial → risk → report`。最小 Chainlit UI 使用相同 Runtime，并保留 CLI 作为降级入口；仓库根目录增加轻量 `chainlit_app.py` 启动入口以保持包导入稳定。
- **修改原因：** 确保任务生命周期长于进程和 UI Session，减少 Resume 输入，并让 Artifact 版本与持久化 State 保持一致。
- **影响范围：** Graph 终止条件、Artifact 写入幂等策略、报告人工意见、Task CLI 和 UI；Day 0 Spike 保持独立不变。
- **验证结果：** Case B 在 Risk 后以 `WAITING_APPROVAL` 暂停，独立进程可仅凭相同 `thread_id` 从 SQLite 读取状态并 Resume；`APPROVE` 生成包含人工意见的报告并进入 `COMPLETED`，`RESEARCH` 生成 v2 Research/Risk Artifact 且保留 v1 后再次暂停，第二次批准后完成。Case A 无 interrupt 直接生成报告。同版本不同内容禁止覆盖，下一版本由 State 引用确定。全量 35 项测试通过；手工三进程演示生成 8 条 Checkpoint；Chainlit 根入口成功加载并监听测试端口。

## 2026-08-13 — Day 5 Retry、Fault Injection、Trace 与 Regression

- **对应阶段：** Day 5 — Research Tool Retry、可控故障注入、JSONL Trace 和五个固定回归 Case。
- **文档原约定：** `RESEARCH_FAIL_FIRST=1` 时首次调用超时、重试成功；重试耗尽设置 `external_research_incomplete=true`；Trace 覆盖 Node、Tool、Retry、Interrupt 和 Resume；维护五个 Regression Cases。
- **实际情况：** 故障注入需要在跨进程 Graph/Resume 中保持 task/tool 维度的一次性状态，单纯进程内计数会在进程重启后重复注入；两个 Research Tool 也需要独立重试和独立失败结果。
- **修改内容：** 在 `traces/.fault_state/` 使用 `task_id + tool_name` 哈希标记首次尝试，目录由 Git 忽略；Research Agent 分别对两个 Tool 执行 `MAX_RETRY + 1` 次尝试，只捕获临时边界错误。耗尽后生成状态为 `FAILED` 的 Tool 结果及 `INCOMPLETE` Research Artifact，Graph State、Risk 和 Report 均披露证据缺口。JSONL Trace 记录 Task、Node、Tool、Retry、Interrupt、Status 和 Resume 摘要，不记录源文档或凭证。
- **修改原因：** 保证故障演示确定、可重复且跨进程一致，同时允许部分调查成功时保留已取得的事实，不因单个 Tool 失败中断整个任务。
- **影响范围：** Research 结果 Schema、Risk/Report 披露、Graph/Runtime Trace、运行目录和测试 Fixture；不修改 `.env`。
- **验证结果：** `RESEARCH_FAIL_FIRST=1` 的真实 stdio MCP 演示中，两个 Tool 各产生一次 `RETRY` 后成功，Trace 共 17 行且包含 Task、Node、Retry、Tool、Interrupt 和 State 事件。永久失败测试中每个 Tool 按配置耗尽重试，State、Research/Risk Artifact 和报告均披露调查不完整。五个具名 Regression Cases 通过；全量 45 项测试、Ruff 和依赖一致性检查通过。
