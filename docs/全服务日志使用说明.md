# 全服务日志使用说明

适用版本：V2-1 / P15。更新日期：2026-09-09。

## 日志在哪里

从仓库运行原有 CLI 或根目录 Chainlit 入口即可启用，无需另开日志服务：

```powershell
python -m app.task_cli start --thread-id demo-001 --case-id case_byd_002594
chainlit run chainlit_app.py
```

每次根服务启动，在工作目录的 `logs/` 下创建一个独立启动目录：

```text
logs/<UTC时间-随机ID>/
  startup.json
  service.0001.jsonl
  service.0002.jsonl
```

一次 CLI 执行对应一个启动批次；一次 Chainlit 服务进程对应一个批次，多个会话/任务共用该批次。该服务创建的 MCP 子进程继承批次，通过独立的本机 TCP 通道汇聚，日志不混入 MCP stdio 或 CLI JSON。MCP 单独运行时创建自己的根批次。

Python 调用方可以使用 `service_session()` 显式包住多个任务；直接调用 `start_task`/`get_task_status`/`resume_task` 时，如果没有宿主服务上下文，会建立本次操作的日志会话。服务日志不改变旧 Trace 和 Checkpoint 的业务用途。

单文件达到 **10,000,000 UTF-8 字节**时，下一条完整记录另起分卷；精确等于上限允许写入。不拆 JSON 行，历史分卷不覆盖、不自动清理。应用日志目录已加入 Git 忽略规则。

## 配置

用户已确认以下默认值，代码默认即可生效。覆盖参数见 `.env.example`；本轮没有修改用户 `.env`。

| 配置项 | 默认值 | 用途 |
|---|---|---|
| SERVICE_LOG_DIR | logs | 日志根目录 |
| SERVICE_LOG_MAX_BYTES | 10000000 | 单卷上限，十进制字节 |
| SERVICE_LOG_QUEUE_CAPACITY | 1024 | 中央待写队列最大记录数 |
| SERVICE_LOG_ENQUEUE_TIMEOUT | 2 | 入队最大等待秒数 |
| SERVICE_LOG_ACK_TIMEOUT | 5 | 等待持久化确认的最大秒数 |
| SERVICE_LOG_SHUTDOWN_TIMEOUT | 10 | 正常退出刷新等待上限 |

记录由单写入线程追加并 flush/fsync，启动清单通过临时文件替换更新。当前所有送入中央队列的事件都采用同步持久化确认，覆盖关键事件逐条同步要求；这是验证项目优先保证诊断可追溯的实现，后续性能优化需保持关键事件保证。

## 如何定位问题

先看 `startup.json` 的 `normal_shutdown`、`gap`、`last_durable_sequence`；再按 JSONL 的 `event_type`、`service`、`node`、`status`、`phase`、`attempt` 和 `sequence` 检索。

- 节点：NODE_START / NODE_END、ROUTE、TASK_STATE。
- 模型：LLM_ATTEMPT_START / LLM_FIRST_TOKEN / LLM_ATTEMPT_END，区分 PROCESS 与 STRUCTURED 阶段；每次调用/重试可关联。
- 校验：LLM_VALIDATION 区分 JSON、Schema、引用和业务校验；传输 SUCCESS 或 HTTP 200 不代表内容被接受。
- 失败：TIMEOUT、RATE_LIMITED、INVALID_JSON、INVALID_SCHEMA、INVALID_CITATION、RETRY、DEGRADED，以及持久化/工具错误。
- 持久化：CHECKPOINT_*、ARTIFACT_*、REPORT_WRITE、AUDIT_EXPORT。

可获得时记录 HTTP 状态、真正的 `x-request-id`、finish_reason 和 usage；无法获取时为 null/UNKNOWN。completion ID 不当成 HTTP 请求 ID。日志不保存完整 Prompt、模型响应、思维链、正文、请求头、Cookie 或异常原始字符串。

自由格式的任务、调用、Provider、模型、Artifact 和异常位置标识采用稳定 SHA-256 引用，避免这些字段夹带敏感文本；原始业务 ID 在 Trace/Checkpoint 中不改名。可以从已知任务 ID 计算检索键：

```powershell
python -c "from credra_agent.observability.events import reference_id; print(reference_id('demo-001'))"
```

旧 Trace 的桥接字段是 `trace_event_ref`，对应原始 `<thread_id>.<行号>` 的同一引用编码；`trace_line` 保留行号。并发上下文通过 ContextVar 和显式 MCP 参数传递，不使用“全局当前任务”。集中接收序号表示写入顺序，不替代业务因果关系。

## 日志故障后的恢复

日志不可达、持续拥塞或写盘失败，会停止派发后续节点。正在执行的 baseline 节点按原有有界逻辑返回并保存结果，在下一个节点执行前暂停。MCP 子进程的日志失败也会传递给主进程，同时保留其业务返回结果。

查询状态：

```powershell
python -m app.task_cli status --thread-id demo-001
```

安全暂停的任务包含：

```json
"execution_blocked": {
  "reason": "LOGGING_UNAVAILABLE",
  "resume_safe": true
}
```

此标记从 SQLite 中“节点开始前的日志门禁异常”投影而来；旧 Graph State 没有新增状态字段，也不依赖服务日志反推任务状态。此前节点的业务状态可能仍显示 RUNNING，界面另外明确显示日志暂停原因。

待任务已经到达该暂停边界，解决磁盘/连接问题并重启故障服务，使其创建健康的新日志批次，再执行：

```powershell
python -m app.task_cli resume --thread-id demo-001 --decision resume_logging
```

如启动时指定了 `--db`/`--data-dir`，查询和恢复时使用相同路径。Chainlit 在恢复服务并重新载入任务后提供“日志恢复后继续”按钮。

该入口只允许恢复明确的节点前日志暂停，不重跑已完成节点，也不能把普通 WAITING_APPROVAL 当作日志故障绕过审批。没有安全暂停标记的中途退出、不确定外部请求或 Artifact 损坏，不能借此自动重发；更细的 Action 账本与请求窗口恢复属于 P14。

## 保证范围

日志故障发生后，已在队列/写盘中的事件可能已经落盘，也可能没有获得 ACK；失败不能解释为“请求未发生”。当前去重窗口是收集器内存中最近 `4 × queue_capacity` 个 event_id，进程重启后不延续；不宣称网络请求或日志 exactly-once。

正常退出在已确认的等待上限内刷新；超过上限会标记失败，不能关闭仍由写入线程使用的文件。进程强制退出后启动清单保持非正常结束，已经同步的完整记录可读；尚未提交或尚未同步的记录可能缺失。真实断电和硬件缓存损坏不在离线测试的无损保证中。

本节点完成的是 baseline 服务日志与节点边界暂停。自主 Agent 的逐 Action 派发、预算、细粒度请求恢复仍在后续 P10–P14；本说明不代表整个 V2-1 已完成。
